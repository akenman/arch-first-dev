## 模型适配

不同 AI 模型的能力差异显著。执行本 skill 时根据当前模型自动调参。

> v2.1 修订原则：模型对自身能力的内省（上下文窗口大小、代码质量自评、缓存行为观察）
> 系统性不可靠。适配参数只允许来自：平台/服务方公布的模型规格、可观察的运行时信号、
> 或保守默认值。参考表是历史快照，可能过时；与自分类冲突时取更保守的值。

### 主策略：4 问题自分类

所有模型（包括未来新模型）优先使用以下 4 个问题自分类，无需更新 skill：

```
问自己 4 个问题 → 得到 4 个策略参数：

1. 上下文窗口多大？
   以平台/服务方公布的模型规格为准；拿不到确切值时按 128K 档执行（最保守）。
   ≥ 500K  → 始终全量加载蓝图
   200K    → Phase 1 全量，Phase 2 按需加载段落
   128K/未知 → 仅加载当前模块+依赖签名

2. 是否支持 thinking / extended reasoning？
   以模型规格为准（探针 3 只做标识匹配，不做运行时猜测）。
   是 → Phase 1 深度推理（探索 2-3 种方案）
         Phase 3 预判高风险路径
   否 → Phase 1 标准推理（1 种方案）

3. 验证强度默认值？
   默认全量逐行对照 + 弱模型默认档（v2.6：骨架先行 scaffold + 每阶段 --gate +
   每条 @FLOW 写 @VERIFY）。自评代码质量不可信——自评系统性偏乐观，会导致
   "信任实现→抽样验证→漏检"。降档条件只有一个：用户明确说"模型很强"。
   上下文预算紧张时的降档顺序：先降蓝图加载量，再降对照抽样，最后才动 @VERIFY
   （机器验证永远最后砍——它是唯一不依赖模型能力的一环）。

4. 是否支持子任务并行？
   以平台能力为准（探针 2 验证）。
   是 → 同层 ≤ 3 并行填充
   否 → 串行填充
```

### 能力探针（每次会话首次触发时执行）

skill 激活后立即运行非侵入式自测，验证适配参数是否与实际环境匹配：

```
探针 1 — 上下文加载验证
  操作: 加载 BLUEPRINT.md（如果存在），观察是否成功
  预期: 全量加载无报错
  异常: 若加载失败 → 降级为按需加载策略

探针 2 — 并行能力验证
  操作: 如有 ≥ 2 个同层 [empty] 模块，尝试并行启动子任务
  预期: 若平台支持 → 子任务成功创建
  异常: 若子任务创建失败 → 标记并行策略为"串行"

探针 3 — thinking 模式检测（基于模型标识）
  操作: 根据模型标识符判断（以平台/服务方公布的规格为准）
  预期: 标识匹配 → 标记 thinking 支持
  异常: 标识未知 → 默认不支持，Phase 1 降为标准推理
  注意: 不尝试运行时探测 thinking token
```

> v2.1 删除了原探针 2（缓存策略推断）：要求模型"观察文件写入的响应特征以推断
> prefix cache 是否生效"在原理上不可实现——模型无法测量工具调用的延迟特征。

探针结果记录在 CHECKPOINT.md 的 `@PROBE` 段：
```
@PROBE 2026-05-10 DeepSeek V4
  上下文: 全量加载 ✅
  并行: 支持 ✅ (≤3)
  thinking: 支持 ✅
```

任一探针失败 → 自动回退到对应降级策略，不阻塞后续流程。
