## 冲突解决

### 场景 1：Phase 3 同时触发健康度自诊 + 差异测试 + 属性测试

```
解决：按序号执行，前一步失败则后续跳过
  1. 健康度自诊 → 如果 < 70 分，先修复蓝图，不进入差异测试
  2. 差异测试 → 如果有 ❌，先修复代码，不进入属性测试
  3. 属性测试 → 在蓝图和代码都健康的基础上才值得做

原因：属性测试最贵（生成大量随机输入），不应在蓝图/代码有问题时浪费上下文
```

### 场景 2：Phase 2 同时触发骨架生成 + 专长分工

```
解决：骨架生成优先，专长分工适配骨架生成产出
  1. 按骨架生成约定产出代码骨架
  2. 专长分工决定谁填充骨架：
     - 架构师角色不参与编译（骨架生成是架构师的"代码输出"）
     - 实现者角色填充骨架中的 TODO
     - 审查者角色验证骨架中的 BEHAVIOR 断言

原因：骨架生成减少了实现者的工作量，专长分工减少了确认偏误，两者互补不冲突
```

### 场景 3：Phase 1 同时触发模式库 + 知识图谱

```
解决：知识图谱验证模式库推荐
  1. 模式库推荐模式组合
  2. 知识图谱验证推荐（历史项目中此组合表现如何）
  3. 如果知识图谱显示此组合历史 Health Score < 70 → 降级为手动设计

原因：模式库是"正向推荐"，知识图谱是"反向验证"，两者互补
```

### 场景 4：多个加载条件同时命中

```
解决：按优先序读取，一轮工作最多读 1 个 reference 文件
  1. 当前 Phase 的必用内容优先（均在 L1，无需读文件）
  2. 用户显式点名的特性优先于自动条件
  3. 其余按本表序号排队，完成当前工作后再读下一个

示例：Phase 2 中同时触发逐行对照与 Rollback → 先读对照（序号 6），
     当前模块填充完成后再读 Rollback（序号 9）
```

### 场景 5：简化模式 vs 完整模式特性集

```
简化模式（≤ 15 接口）：
  默认不加载：边界矩阵、骨架生成、蓝图属性测试、蓝图知识图谱
  原因：小项目不需要重量级工具

完整模式（> 15 接口）：
  全部特性可用，按优先序加载

例外仲裁：用户显式请求的特性（如"生成代码骨架"）总是允许加载，
  但加载前提示一句"当前项目为简化模式，此特性为重量级工具"，由用户最终决定。
  （这同时是 SKILL.md 读取纪律第 3 条与本场景的统一规则）
```
