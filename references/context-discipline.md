# Phase 2 填充纪律（上下文 / 对照 / 检查点 / 测试）

> 加载条件：Phase 2 填充期间——上下文纪律、逐行对照、模块 [done] 后动作、上下文压力信号。
> 特性分诊标签：【已验证】= 有 eval 实证；【未验证】= 设计存在但从未被 eval 触达，
> 使用前请自行验证。证据矩阵见 README.md「特性 × 证据」。按 SKILL.md L3 路由器读取，未命中不读。

## 上下文压力感知【已验证-机制】【未验证-阈值】

AI 无法直接读取"上下文使用率百分比"，改用 4 个可观察信号：

| 信号 | 触发条件 | 判断 |
|------|---------|------|
| 旧内容回流 | 工具输出中重复出现前 3 轮已处理过的文件内容 | 🟠 |
| 推理步数增加 | 完成一个填充循环的工具调用数 > 8 次（基准 4-6 次） | 🟡 |
| 频繁读蓝图 | 同一次填充中读 BLUEPRINT.md 超过 2 次 | 🔴 |
| 错误模式重复 | 连续出现同类接口不匹配 | 🟠 |

判断逻辑（模型无法逐出自己的上下文，可用杠杆只有四个——控制读什么、控制写什么、
/compact、委派子任务，所有响应都落在真实杠杆上）：

```
🟢 无信号触发 → 正常继续
单 🟡 → 继续填充，但停止重读蓝图与已完成模块的实现文件（信息只从接口签名与 @DATA 取）
单 🟠 → 写 CHECKPOINT.md；后续填充优先委派子任务（子代理天然获得干净上下文）
🟠 ×2+ 或 🔴 → 先写 CHECKPOINT.md，再执行 /compact（或平台等价物），从 CHECKPOINT 恢复后继续
🟠 + 🔴 同时出现 → 写入 CHECKPOINT.md，建议用户开新会话从 checkpoint 恢复
```

## 上下文纪律（Context Discipline）【已验证-间接】

原"上下文预算管理器"要求模型估算 token 并计算剩余预算——两个数字模型都拿不到，
估算会静默失真。v2.1 起替换为可执行纪律：

```
1. 读什么：填充期只读 3 类内容——当前模块蓝图条目、依赖模块接口签名、@CROSSCUT。
   已完成模块的实现文件不再读取（行为信息从接口签名与 @DATA 获取）。
2. 写什么：同层模块全部 [done] 后一次批量更新 @PROGRESS；CHECKPOINT.md 覆盖写。
3. 何时压缩：出现 🟠×2+/🔴 信号时 /compact；compact 前必须先写 CHECKPOINT.md。
4. 何时委派：单个模块实现预计超过 ~200 行，或压力 ≥ 🟠 时，把该模块委派给子任务
   （子代理上下文 = 蓝图条目 + 依赖签名 + @CROSSCUT，天然干净），主会话只收结果。
5. 何时新会话：CHECKPOINT + 用户开新会话是最后兜底，成本高于 compact。
```

与上下文压力感知的关系：压力感知回答"何时行动"，本节回答"行动的具体动作"。

### 1. Behavior-Code 逐行对照【已验证】

LLM 对自己的输出有确认偏误——自我批评的检查清单容易被"逐项打勾通过"。替代方案：
把刚实现的代码和 BEHAVIOR 声明逐行对照，不做主观判断：

```
① pre 的落实证据   蓝图声明: pre: name 非空 → 代码证据: if not name: raise ValueError(...)
② post 的落实证据  蓝图声明: post: 返回 id > 0 → 代码证据: cat = {"id": _next_id, ...}
③ error 的落实证据 蓝图声明: error: ValueError → 代码证据: 所有 if...raise 路径覆盖声明
④ side-effect 证据 蓝图声明: _data 追加一条 → 代码证据: _data.append(cat)
```

对比规则：**不要问"你觉得做得对吗"——只找"声明是否在代码中有对应行"**。找不到就是漏了。

对照范围分级：
```
微项目档（≤8 接口）→ 跨模块接口全量 + 模块内部接口抽查 1-2 个
简化模式（9-15 接口）→ 全量
完整模式（>15 接口）→ 按风险导向分级（入口接口 / 被 ≥2 模块依赖的接口 /
                     操作 @EXTERNAL 的接口全量，其余信任实现）
```

### 2. Auto-Checkpoint【已验证-使用】【未验证-恢复价值】

每个模块标记 [done] 后，覆盖写 `.arch/CHECKPOINT.md`：

```
@CHECKPOINT
  时间: Phase-2 / auth 完成
  状态: 2/6 模块 done
  最后变更: @CHANGE_003 — auth.login 增加空密码校验
  上下文状态: 🟡
```

自动写入规则：
```
每次 [done] 后 → 覆盖 CHECKPOINT.md
每次填充异常处理后 → 追加到 CHECKPOINT.md
Phase 3 完成后 → CHECKPOINT.md 标注 [COMPLETE]
微项目档（≤8 接口）→ 仅在 Phase 切换时覆盖写（小项目模块间写 checkpoint 的
  开销大于其恢复价值）
```

### 3. Design Decision Log【已验证】

@CHANGE 记录"改了什么"，@DECISION 记录"为什么这么改"。触发时机：从多个可行方案
中选了一个、接口设计有合理替代方案、为可扩展性做了取舍、性能/安全/兼容性权衡。

```
@DECISION_001
  场景: transactions 模块的 filter 参数设计
  选择: 用 dict 而非 SQL-like 字符串
  理由: 保持内存存储和未来数据库存储的接口兼容性
  替代方案考虑过: 字符串表达式、链式调用、builder 模式
  影响: 未来切换到 SQLite 时 filter dict 可以直接映射到 WHERE
```

### 4. @CHANGE 与 @DECISION 的边界【已验证】

```
@CHANGE 记录"改了什么"（事实）：任何对 BLUEPRINT.md 的修改都要记，数量不设上限
@DECISION 记录"为什么这样设计"（理由）：只记有替代方案的、非显而易见的选择，
  数量少——"别人会问为什么"的情况才记
两者不冲突，同一修改可以同时有 @CHANGE 和 @DECISION。
```

### 5. 并行填充【未验证】

严格限定：同一 @BUILD_ORDER 层级 + 双方依赖都已 [done] 的模块才能并行。
一个 AI 会话内不支持并行（上下文只有一个推理路径）；并行适用于平台子任务工具，
每个子 agent 的上下文 = 蓝图 + 自己负责的模块。平台不支持 → 串行。

### 6. 扩展状态说明【已验证】

```
[deferred]  延迟实现：模块状态 [deferred]，@CHANGE 记原因和计划版本；
            Phase 3 跳过其流验证和空位检查；依赖它的模块需同步标记或提供 stub
[wontfix]   已知不修复：@CHANGE 记原因；Phase 3 跳过其边界/错误链检查
[removed]   已废弃删除：@CHANGE 记替代方案；依赖方更新依赖字段；删目录、更新 @BUILD_ORDER
```

### 7. 退出条件【已验证】

```
✓ Phase 3 验证全部通过 → 项目已完整实现，退出 skill
✓ 单文件改动/加注释/格式化 → 不触发 skill
✓ 加新功能/重构模块/修 bug → 迭代模式
退出后 BLUEPRINT.md 保留在 .arch/ 作为架构文档存档，不再占用上下文。
```

## 测试策略（最小化）【已验证】

Phase 2 每模块 [done] 后：
  - 按项目语言约定创建测试文件（test_<module>.py / <module>.test.ts / <module>_test.go）
  - 每个对外接口至少一个 happy-path 用例
  - 边界矩阵 ✓ 维度 → 至少 1 个边界测试；错误链每条路径 → 至少 1 个触发测试

  微项目档（≤8 接口）：只为跨模块接口生成测试；模块内部接口由 Phase 3 ⑦ 兜底。

  测试文件豁免约束 5（模块边界）：测试可以跨模块调用，用于集成验证。

Phase 3 验证通过后运行全量测试套件；覆盖率不做硬性要求（重点在关键路径和边界）。
