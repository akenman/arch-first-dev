# 蓝图知识图谱

> 加载条件：用户明确说"参考历史项目"/"相似项目"时
> 难度：⭐⭐⭐⭐⭐（最高，需要积累 20+ 项目数据）
>
> 状态（v2.1）：**实验性特性，默认关闭**。skill 主流程不依赖本文件；
> 需 ≥ 20 个项目数据才有预测价值，冷启动期（绝大多数用户）建议不使用。
> 隐私敏感用户可直接忽略本特性（数据仅在本机，见下文"隐私保护"）。

## 概念

每个完成的 BLUEPRINT.md 都是一个结构化的架构知识。当前这些知识是孤立的——项目 A 的蓝图对项目 B 毫无帮助。蓝图知识图谱将跨项目的架构知识提取、索引、复用，形成**数据驱动的架构决策系统**。

```
当前：项目 A 蓝图 ← 孤立 → 项目 B 蓝图
未来：项目 A 蓝图 → 提取模式 → 知识图谱 ← 匹配模式 ← 项目 B 蓝图
```

## 知识提取

每个 Phase 3 完成后，自动从 BLUEPRINT.md 提取架构知识：

### 提取内容

```
1. 模块拓扑
   - 模块数 / 接口数 / 依赖数
   - 最深依赖链长度
   - 是否有循环依赖（Phase 1→2 预检 ⑥ 结果）
   - 扇出度（被依赖最多的模块）

2. 接口密度
   - 平均每模块接口数
   - 最大/最小接口数模块
   - 简化格式接口占比（纯函数/UI/配置）

3. 数据流复杂度
   - @FLOW 条数
   - 平均每条涉及模块数
   - 异步流占比
   - 最长 @FLOW 的步骤数

4. 外部依赖模式
   - 数据库/API/消息队列的使用组合
   - @EXTERNAL 数量
   - 故障模式覆盖率

5. 变更模式
   - @CHANGE 数量
   - 触发原因分布（接口缺失/多余/不匹配/拆分/蓝图问题）
   - rollback 次数
   - 蓝图修正协议触发次数

6. 健康度轨迹
   - Phase 1/2/3 各阶段的 Health Score
   - 扣分项分布
```

追加到 `~/.arch-knowledge/graph.jsonl`（每行一个项目的知识）：

## 应用场景

### 1. 相似项目匹配

Phase 1 启动时，自动匹配历史相似项目：

```
@MATCH_REPORT
  当前需求: 博客系统（用户认证 + 文章 CRUD + 评论 CRUD + API 前端）
  
  最相似项目:
    1. task-cli (相似度 45%) — 共享 CRUD 模式，但无用户认证和 API
    2. (无更多历史项目)
  
  建议: 复用 CRUD 模式（已验证），新增 user-auth + api-frontend 模式
```

匹配算法：
```
相似度 = Σ(共享模式权重) / Σ(当前需求模式权重) × 100%
模式权重: crud=1, user-auth=2, event-driven=2, cli-frontend=1, api-frontend=1
```

### 2. 蓝图健康度预测

Phase 1 完成后，基于历史数据预测蓝图质量：

```
@HEALTH_PREDICTION
  当前: 4 模块 / 15 接口 / 3 层深度
  历史同类项目平均 Health Score: 88
  你的 Health Score: 65
  
  偏低原因分析:
    - 4 模块 15 接口的项目，历史平均 @CHANGE 2 条，你已有 5 条
    - 最深依赖链 3 层，历史同类项目平均 2 层
    - 建议: 检查是否可以扁平化依赖（合并某些模块）
```

### 3. 反模式预警

Phase 1 完成后，基于历史数据预警常见反模式：

```
@ANTI_PATTERN_ALERT
  ⚠️ 深依赖链预警
  当前最深依赖链: 6 层
  历史数据: 超过 5 层的项目 rollback 率 60%（样本: 8 个项目）
  建议: 考虑引入事件驱动模式解耦
  
  ⚠️ 大模块预警
  当前最大模块: tasks（7 个接口）
  历史数据: 接口数 > 6 的模块 @CHANGE 率 45%
  建议: 考虑拆分为 tasks-core + tasks-filter
```

### 4. 模式推荐

Phase 1 启动时，基于需求关键词推荐模式组合：

```
@PATTERN_RECOMMENDATION
  需求关键词: "博客", "用户", "文章", "评论", "API"
  推荐模式组合:
    1. user-auth (jwt) — 用户注册/登录/鉴权
    2. crud (Post) — 文章增删改查
    3. crud (Comment) — 评论增删改查
    4. api-frontend — RESTful API 接口层
  
  历史验证: 此组合在 3 个历史项目中使用，平均 Health Score 90
  预计蓝图完成度: 85%（需补充: 文章-评论关联 @FLOW、权限控制规则）
```

## 隐私保护

```
只存储架构元数据（模块数/接口数/依赖深度），不存储业务逻辑
用户可选择退出: 在项目 .arch/ 目录下创建 .no-knowledge 文件
数据完全本地，存储在 ~/.arch-knowledge/，不上传任何服务器
知识图谱仅本机可用，不跨设备同步
```

## 与其他特性的关系

```
知识图谱 + 蓝图模式库:
  模式库定义"有哪些模式可用"
  知识图谱提供"这些模式在历史项目中表现如何"
  组合使用: 模式推荐 = 模式库匹配 + 知识图谱验证

知识图谱 + 蓝图漂移检测:
  漂移检测记录"蓝图和代码的差异"
  知识图谱汇总"哪些模块最容易漂移"
  组合使用: 对历史漂移率高的模块加强检测频率

知识图谱 + 蓝图健康度自诊:
  健康度自诊给出"当前蓝图的绝对分数"
  知识图谱提供"同类项目的平均分数"
  组合使用: 相对健康度 = 绝对分数 / 历史平均分数
```

## 冷启动策略

知识图谱需要数据积累才能发挥作用。冷启动阶段（< 5 个项目）：

```
0 个项目: 知识图谱不可用，仅使用模式库
1-4 个项目: 知识图谱仅提供相似项目匹配，不提供预测和预警
5-19 个项目: 知识图谱提供匹配 + 预测 + 预警，但标注"低置信度"
≥ 20 个项目: 知识图谱全功能可用，置信度标注为"高"
```

加速积累方式：
```
1. 逆向蓝图也算：对现有项目执行逆向蓝图，完成后同样提取知识
2. 手动导入：用户可以导入其他项目的 BLUEPRINT.md 到知识图谱
3. 社区共享（未来）：用户可选择上传脱敏后的架构元数据到社区
```
