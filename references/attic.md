### 5. 多会话协作

> ⚠️ v2.4 处置建议：**有 git 的团队请用 git 分支替代本协议**（每个会话一个分支，
> 蓝图变更走 PR review——比文件锁可靠且可归责）。本节保留给无 git 的极端环境。

适用场景：多人并行开发同一蓝图的不同模块。

**模块锁协议**（`.arch/LOCKS.md`）：

```
@LOCKS
  storage        [claimed]  session-abc123  (2026-05-10 14:30)
  tasks          [claimed]  session-def456  (2026-05-10 14:31)
  stats          [free]
  reports        [free]
```

规则：
  - 填充模块前，检查 LOCKS.md 中该模块状态
  - [free] → 标记 [claimed] + 会话 ID + 时间戳 → 开始填充
  - [claimed] 且距上次更新时间 > 30 分钟 → 可抢占（原会话可能已失效）
  - [done] → 不可抢占，已完成
  - 每次 CHECKPOINT 写入时同时更新 LOCKS.md 的时间戳（续约）

**合并协议**：

两个会话完成各自模块后：
  1. 任一会话读取完整 BLUEPRINT.md + LOCKS.md
  2. 检查所有 [done] 模块的接口签名是否有冲突（同名不同签名）
  3. 无冲突 → 合并，运行 Phase 3 全量验证
  4. 有冲突 → 冲突模块重置为 [in progress]，按构建顺序重新填充
  5. 合并完成后，LOCKS.md 归档到 .arch/LOCKS_ARCHIVE.md

**CHECKPOINT 协调**：

每个会话的 CHECKPOINT.md 追加同行信息：
```
@PEERS
  session-abc123: storage [done]       (最后更新: 14:35)
  session-def456: tasks [in progress]  (最后更新: 14:33)
```
读取 BLUEPRINT.md 时同时读取所有活跃会话的 CHECKPOINT.md，避免重复工作。

**限制**：多会话协作要求 BLUEPRINT.md 和 LOCKS.md 共享（如通过 Git），本 skill 不负责文件同步机制。


### 8. Rollback 协议（源自 Cursor Rules 实践）

当 @CHANGE 的修改引发下游模块的连锁问题时，执行 rollback：

```
触发条件：下游模块填充时发现上游模块的接口变更导致无法对接

Rollback 步骤：
  1. 标记当前模块为 [blocked]
  2. 确认引发问题的上游 @CHANGE 编号
  3. 回滚该 @CHANGE：将上游模块的接口恢复为变更前的签名
  4. 恢复后上游模块状态重置为 [in progress]
  5. 在 @CHANGE 中追加 rollback 记录：
     @CHANGE_004
       触发: Rollback from budgets.checkBudget
       原因: auth.validateToken 返回了额外的 role 字段，budgets 未预期
       操作: auth.validateToken 返回值恢复为 {userId}（去掉 role）
       影响: auth 回到 [in progress]，需要重新实现
       约束: 全部通过

不触发 rollback 的条件：
  - 下游模块尚未开始填充（直接修改上游接口，无成本）
  - 下游模块可以直接适配新接口且受影响文件 ≤ 2 个（> 2 个时执行 rollback）
```


## 大型项目蓝图分解策略

> 加载条件：模块数 ≥ 15 或蓝图预估超过上下文窗口 40% 时

当项目规模较大时，单一 BLUEPRINT.md 可能超出上下文承载能力。此时按子系统拆分：

```
拆分规则：
  1. 识别子系统边界：按业务域划分（如用户系统、订单系统、支付系统）
  2. 每个子系统一个子蓝图：BLUEPRINT-<subsystem>.md
  3. 创建根蓝图 BLUEPRINT.md：只包含 @META + 子系统间 @FLOW + 跨子系统 @DATA
  4. 子系统内部遵循完整蓝图格式（@MODULE / @FLOW / @DATA / @BUILD_ORDER 等）

子蓝图间引用协议：
  - 子蓝图引用其他子系统的接口时，使用 @EXTERNAL 声明（类型: 内部子系统）
  - 格式与外部依赖一致，但额外标注来源子系统：
    @EXTERNAL 用户系统（内部子系统）
      类型: 内部子系统
      蓝图: BLUEPRINT-user.md
      契约:
        - getUser(id) → User
        - 仅订单系统可以调用
      故障模式: 用户不存在 → 返回 null

根蓝图职责：
  - 不包含具体模块，只包含子系统间的数据流和共享数据结构
  - @BUILD_ORDER 按子系统粒度排序
  - Phase 2 填充时，按子系统逐个展开子蓝图
  - 根蓝图与每个子蓝图分别通过 validate_blueprint.py 校验
    （子蓝图间引用的接口以 @EXTERNAL 条目参与消费者检查）

上下文管理：
  - 同一时刻只加载一个子蓝图 + 根蓝图
  - 切换子系统时，按上下文纪律行动：不再读取当前子蓝图的实现文件，必要时 compact
  - CHECKPOINT.md 记录当前活跃子系统
```

## AI 专长分工（Specialized Agent Roles）

> 加载条件：平台支持子任务（Task 工具）时自动启用；不支持时退化为角色转换模式
> 难度：⭐⭐（低-中）

### 问题

一个 AI 同时做设计、实现、验证三种工作，存在**确认偏误**——自己设计的架构，自己实现时不会质疑；自己写的代码，自己验证时容易放过。同时，三种工作需要不同的上下文，混在一起浪费上下文窗口。

### 三角色模型

```
角色 1 — 架构师（Architect）
  负责: Phase 1 画蓝图 + 蓝图修正
  思维模式: 发散 — 探索多种方案，权衡取舍
  上下文: 完整需求 + 项目文件列表（不读实现代码）
  产出: BLUEPRINT.md
  角色指令: "你是架构师，只设计不实现。每个设计选择必须有理由。
            不确定时列出 2-3 种方案让用户选择，不要自行决定。"

角色 2 — 实现者（Implementer）
  负责: Phase 2 逐格填充
  思维模式: 收敛 — 严格按蓝图实现，不做设计决策
  上下文: 当前模块 @MODULE + 依赖接口签名 + @CROSSCUT
  产出: 模块代码 + 测试
  角色指令: "你是实现者，严格按蓝图签名实现。发现蓝图问题不要自行修改，
            而是报告异常（填充异常 6 种），由架构师处理。
            不确定的实现细节选择最简方案，记录 @DECISION。"

角色 3 — 审查者（Reviewer）
  负责: Phase 3 验证 + 差异测试
  思维模式: 批判 — 主动寻找不一致，不信任实现
  上下文: BLUEPRINT.md + 所有模块的接口签名（不读实现代码）
  产出: 验证报告 + 差异报告
  角色指令: "你是审查者，不信任任何实现。只对照蓝图验证，
            发现任何不一致都报告。不做修改建议，只报告事实。"
```

### 协作协议

```
架构师 → 实现者: 蓝图（@MODULE + @FLOW + @DATA + BEHAVIOR 声明）
实现者 → 架构师: 异常报告（填充异常 6 种）
实现者 → 审查者: 完成通知（模块 [done]）
审查者 → 实现者: 差异报告（需修复的项）
审查者 → 架构师: 蓝图修正建议（设计层面的问题）

信息流向严格单向，避免循环：
  架构师 ──蓝图──→ 实现者 ──完成通知──→ 审查者
     ↑                 │                      │
     └── 异常报告 ──────┘                      │
     └────────────── 修正建议 ←────────────────┘
```

### 子任务模式（平台支持 Task 工具时）

```
Phase 1: 主 Agent 作为架构师，完成蓝图设计
Phase 2: 对每个 [empty] 模块，启动子任务：
  子任务上下文 = 蓝图 + 当前模块 @MODULE + 依赖接口签名 + @CROSSCUT
  子任务指令 = 实现者角色指令 + 具体模块名
  子任务产出 = 模块代码 + 测试 + 异常报告（如有）
Phase 3: 主 Agent 切换为审查者，执行验证
```

### 角色转换模式（平台不支持子任务时）

单 Agent 在 Phase 切换时做角色转换。上下文无法"清空"（追加式），
真实的转换动作是：写 checkpoint → 压缩 → 带着压缩后的最小上下文继续。

```
Phase 1 → Phase 2 时：
  写 CHECKPOINT.md → 执行 /compact（摘要保留蓝图与接口签名）→ 以实现者角色继续
  效果：Phase 1 的发散推理被压缩掉，上下文只留契约

Phase 2 → Phase 3 时：
  写 CHECKPOINT.md → 执行 /compact（摘要保留蓝图、接口签名与验证要求）→ 以审查者角色继续
  效果：实现细节被压缩，为验证腾出上下文

角色转换时必须：
  1. 先写 CHECKPOINT.md（压缩可能丢细节）
  2. /compact 的指示中明确保留蓝图、接口签名、当前进度
  3. 从 CHECKPOINT.md 恢复工作状态
```

### 与其他特性的关系

```
专长分工 + 上下文纪律：
  角色转换时遵循上下文纪律（checkpoint → compact → 最小上下文继续）
  架构师阶段 → 不读实现文件
  实现者阶段 → 只读当前模块条目 + 依赖签名 + @CROSSCUT
  审查者阶段 → 只读蓝图与接口签名，不读实现代码

专长分工 + 蓝图差异测试：
  审查者角色负责执行差异测试
  实现者角色不参与验证，消除确认偏误
```
